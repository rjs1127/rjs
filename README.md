## v7.45 — 이어보기 대기 상태 종료 시 진도 보존

### 확인된 원인
- 이어보기 안내가 표시된 상태에서 아무 동작 없이 리더를 닫아도 `finalizeReaderClose()`가 `saveReaderProgress()`를 무조건 실행함
- 이때 리더는 아직 초기 위치(`scrollTop = 0` 또는 첫 페이지)에 있으므로 기존 진도가 0%로 덮어써질 수 있었음
- 따라서 이어보기 이동 자체가 정상이어도 단순 열기/닫기만으로 저장 진도가 초기화되는 현상이 발생함

### 수정
- 이어보기 안내가 아직 활성 상태이고 사용자가 초기 위치에서 실제로 이동하지 않은 경우 닫기 시 진도 저장을 생략하도록 변경
- 스크롤 모드는 의미 있는 스크롤 이동 여부, 페이징 모드는 페이지 이동 여부를 함께 확인하도록 처리
- 리더 종료 직전 남아 있는 지연 진도 저장 타이머를 취소해 종료 후 0%가 뒤늦게 저장되는 경로도 차단
- 사용자가 실제로 스크롤하거나 페이지를 이동한 경우에는 기존처럼 현재 진도를 정상 저장

### 커밋 메시지 요약
- 이어보기 대기 상태에서 리더만 닫을 때 기존 진도가 0%로 초기화되는 문제 수정
- 미사용 종료 시 기존 진도 보존 및 종료 지연 저장 타이머 차단

### 유지
- v7.44에서 정상 확인된 스크롤 이어보기 이동 로직 변경 없음
- 페이징 진도 환산/이어보기 위치 계산 로직은 이번 버전에서 변경하지 않음
- 서버/API/Cloudflare 설정 변경 없음
- 배포 및 환경설정 파일 미포함

## v7.44 — 스크롤 이어보기 저장값 소실 수정

- 이어보기 안내를 표시하는 순간의 저장 위치를 `readerResumeSaved`에 별도 보관하고, 버튼 클릭 시 해당 스냅샷을 우선 사용하도록 변경

## v7.39 — 스크롤 이어보기 초기 0% 덮어쓰기 수정

### 확인된 원인
- v7.21에서 페이지/스크롤 모드 전환 로직이 추가된 뒤, 작품을 처음 열 때 `setReaderDisplayMode(..., offset: 0)`이 실행됨
- 이 초기 레이아웃 정렬 과정에서 `jumpReaderPanelTo(0)` / `temporarilySuspendProgressSave()`가 지연 저장을 예약함

- 사용자가 그 뒤 `이어보기` 버튼을 누르면 기존 저장 진도가 이미 0%로 바뀌어 `getReaderProgress()`가 이어볼 위치가 없다고 판단할 수 있었음

### 수정

- 기존 저장된 진도는 이어보기 버튼을 누를 때까지 그대로 보존함
- 사용자가 실제 스크롤하거나 이어보기 이동을 수행한 이후의 정상 진도 저장은 기존대로 유지함

## v7.38 — 스크롤 모드 이어보기 문자 좌표 수정

### 추가 확인된 원인
- 장편 TXT의 스크롤 진도 저장에서 화면상 `chunk 높이 비율`을 `chunk 글자 비율`처럼 사용하고 있었음
- 줄바꿈, 화면 폭, 글씨 크기, 빈 줄 등에 따라 픽셀 높이 비율과 실제 문자 위치 비율은 달라질 수 있음
- 복원 시에도 `offsetTop`을 readerPanel의 `scrollTop`과 같은 좌표계로 취급해 DOM 구조/브라우저에 따라 목표 위치가 어긋날 수 있었음

### 수정
- 현재 화면 상단 부근에 실제로 표시된 문자를 Range 좌표로 찾아 정확한 문자 위치를 진도로 저장
- 이어보기 시 저장된 문자 위치를 현재 화면 레이아웃에서 다시 Range 좌표로 변환해 이동
- `getBoundingClientRect()`와 현재 readerPanel scrollTop을 이용해 서로 다른 DOM 좌표계를 명시적으로 변환
- Range 좌표를 얻지 못하는 브라우저에서는 기존 높이 비율 방식을 안전 fallback으로 유지
- 일반 TXT의 기존 percent 기반 이어보기와 페이지 모드는 변경하지 않음

### 유지
- v7.37 이전 진도 데이터 호환 유지
- v7.36 상단 설정 아이콘 조건 유지
- 서버/API/KV/D1 변경 없음

## v7.37 — 스크롤 모드 이어보기 좌표 수정

### 확인된 원인

- 짧은 TXT는 컴팩트 헤더 전환이 완료된 후 최종 스크롤 높이로 이어보기 위치를 계산

## v7.35 — 이어보기 이동 재보강

### 추가 확인된 문제
- 장편 뷰어가 백그라운드에서 다음 chunk를 미리 렌더링 중일 때 `renderLargeReaderThrough()`가 바로 종료될 수 있었음
- 이 타이밍에 이어보기를 누르면 목표 chunk가 DOM에 아직 없어서 버튼을 눌러도 이동하지 않는 경우가 있었음
- 컴팩트 헤더 전환 전의 높이로 목표 위치를 계산하면 모바일에서 실제 위치가 달라질 수 있었음

### 수정
- 다른 chunk 렌더링이 진행 중이면 이어보기 로직이 최대 5초까지 완료를 기다림
- `ensureLargeReaderChunkRendered()`를 추가해 목표 chunk가 실제 DOM에 생성됐는지 확인
- 이어보기 시 먼저 컴팩트 헤더로 전환한 뒤 최종 레이아웃 기준으로 목표 위치 계산
- 위치 이동을 최대 4번 검증/재시도
- `scrollTop`과 `scrollTo({behavior:"auto"})`를 함께 사용해 모바일 WebKit 대응 강화
- 성공했을 때만 이어보기 안내창을 숨김
- 실패하면 안내창을 유지하고 `다시 시도해 주세요` 메시지를 표시해 조용히 실패하지 않도록 변경
- 짧은 TXT와 페이지 모드 이어보기도 동일하게 안정화

### 유지
- v7.34 percent 우선 위치 계산 유지
- v7.33 Safari 70k chunk 안정화 유지
- 서버/API/KV/D1 변경 없음


## v7.34 — 이어보기 위치 이동 수정

### 원인
- 장편 이어보기는 기존에 `chunkIndex + chunkRatio`를 우선 사용했음
- Safari 안정화를 위해 Safari chunk 크기를 70,000자로 변경하면서 예전에 저장된 chunk 번호와 현재 chunk 번호가 다른 위치를 가리킬 수 있었음
- 모바일 Safari 내부 스크롤에서는 레이아웃 정리 중 `smooth` 스크롤이 취소되는 경우도 있었음

### 수정
- 이어보기 기준을 `progressPercent` 우선으로 변경
- 퍼센트 → 전체 TXT 문자 위치 → 현재 브라우저의 chunk 위치로 다시 계산
- Chrome에서 저장한 진도를 Safari에서 열거나 chunk 전략이 바뀌어도 같은 진도율 위치로 이동
- 장편은 현재 브라우저 기준 target chunk까지 먼저 렌더링한 후 위치 이동
- 이어보기 위치 이동은 `smooth` 대신 즉시 `scrollTop` 적용 후 다음 frame에서 실제 위치를 재검증
- 짧은 TXT 이어보기와 페이지→스크롤 모드 전환 위치 복원도 동일한 검증형 이동 사용
- 페이지 모드 이어보기 역시 저장 퍼센트를 우선 사용

### 영향
- D1 스키마 변경 없음
- 기존 chunkIndex/chunkRatio 값은 호환용 fallback으로 유지
- 서버/API/KV/Drive 호출 추가 없음

## v7.33 — Safari 스크롤 뷰어 안정화

### 증상
- 일부 Safari 사용자에서 TXT 본문이 처음에는 보이지만 아래로 스크롤하면 본문이 비거나 중간에서 끊긴 것처럼 보이는 현상 대응
- 모든 Safari에서 재현되는 현상은 아니므로 WebKit의 대용량 텍스트 / 내부 스크롤 repaint 차이를 우선 방어

### Safari 전용 보정
- Safari에서 장편 virtual chunk 크기를 약 180,000자 → 70,000자로 축소
- 첫 화면에서 Safari는 일반 브라우저보다 한 chunk 더 미리 렌더링
- 다음 chunk도 스크롤 끝에 닿기 훨씬 전부터 선렌더링
- 스크롤 이벤트 외에 `touchend`, `visualViewport resize`에서도 장편 선렌더링을 한 번 더 확인
- chunk 추가 직후 Safari에서 가벼운 layout checkpoint를 실행해 paint 누락 가능성 감소
- 각 virtual chunk를 독립적인 WebKit paint block으로 처리

### 모바일 Safari viewport
- 지원되는 Safari에서는 스크롤 모드 뷰어 높이에 `100svh` 사용
- 주소창/하단 툴바가 접히고 펼쳐질 때 `100dvh`가 계속 변하면서 내부 reader가 재배치되는 현상 완화
- 페이지 모드는 기존 구조 그대로 유지

### 영향
- Safari가 아닌 브라우저의 기존 180,000자 chunk 구조는 유지
- 서버/API/KV/Drive/D1 호출 수 변화 없음
- 이미 받아온 TXT의 브라우저 렌더링 단위만 Safari에서 더 작게 나눔
- 기존 진도/읽음/컴팩트/페이지 모드 기능 유지

## v7.13 — 관리자 리소스 사용 현황 대시보드

### 관리자 `리소스` 탭
- 관리자 페이지에 `리소스` 탭 추가
- 현재 앱이 실제로 사용하는 Cloudflare binding 상태를 한 화면에서 확인
  - KV `ARCHIVE_KV`
  - D1 `USER_DB`
  - R2 `ARCHIVE_BODY`
  - Workers / Pages Functions Analytics 연결 상태
- Google Drive / Google Sheets가 언제 호출되는지도 기능별 사용 구조에 표시

### KV 현황
- 현재 namespace의 전체 key 수 표시
- TXT 본문 `body:*` cache key 수 별도 표시
- Drive 목록 / POSTYPE index / 작품형태·상태 override / 사이트 설정 / 본문 cache 등 용도별 key 개수 분류
- 기본 `빠른 새로고침`은 key 목록만 확인하여 불필요한 value read를 만들지 않음
- `KV 용량 정밀 측정` 버튼을 따로 제공
  - 실행 전에 현재 key 수만큼 KV get이 발생한다는 확인창 표시
  - 사용자가 명시적으로 실행한 경우에만 각 value를 읽어 실제 byte 합계 계산
  - 정밀 측정 자체가 소비하는 KV read 수를 관리자에게 명확히 고지

### D1 현황
- 사용자 계정 / 로그인 세션 / 개인 독서 기록 / 방문 원본 / 방문 집계 / 일별 집계 / 시스템 메타 table별 row 수 표시
- 전체 app-managed row 수 표시
- D1 환경에서 `PRAGMA page_count/page_size`를 제공하는 경우 현재 DB 파일 크기도 계산
- 사용자 ID나 독서기록 원문은 리소스 화면에 노출하지 않고 row 개수만 조회

### R2 현황
- `ARCHIVE_BODY` binding이 없으면 `미사용`으로 표시
- binding이 아직 남아 있으면 object 수와 byte 합계 표시
- 현재 운영 TXT 본문 코드는 R2를 사용하지 않는다는 점을 명시하여 레거시 binding/객체 여부를 확인 가능

### 실제 일일 quota 사용량
- 현재 앱 binding만으로는 Cloudflare 계정의 `오늘 Workers 호출수 / KV read·write / D1 rows read·written / CPU` Analytics를 정확히 가져올 수 없음을 관리자 화면에 명시
- 실제 Cloudflare Analytics까지 관리자에 표시하려면 별도 Cloudflare Analytics API credential 연결이 필요
- 정확한 사용량을 보기 위해 요청마다 별도 계측 write를 추가하는 방식은 리소스를 더 소비하므로 이번 버전에는 도입하지 않음

### 기능별 사용 구조
- 콘텐츠 목록 열기
- TXT 본문 KV cache hit
- TXT 본문 KV cache miss
- 이어보기/북마크/읽음 저장
- Drive 다시 읽기
- POSTYPE 동기화
각 동작이 KV / D1 / Google Drive·Sheets를 어떻게 사용하는지 표로 표시

- 실제 `읽음`은 뷰어가 문서의 진짜 마지막 지점에 도달했을 때만 기록
- 일반 TXT는 실제 스크롤 하단 140px 이내 + 의미 있는 스크롤이 있을 때 읽음 처리
- 긴 TXT는 마지막 virtual chunk까지 실제 렌더링된 상태에서 최종 하단에 도달해야만 읽음 처리
- 중간 chunk의 바닥까지 내려온 상태는 절대 읽음으로 처리하지 않음

### 이어보기
- 95~99%여도 실제 끝까지 읽지 않았다면 `읽는 중`과 `이어보기` 유지
- 읽지 않은 작품의 화면 표시 진도는 최대 99%로 표시
- 실제 끝 도달 시에만 진도 100% + `readAt` 저장
- 기존 v7.5의 첫 의미 있는 스크롤 즉시 저장, 60초 원격 동기화, pagehide/visibilitychange 저장은 그대로 유지

### 기존 95% 읽음 오판 데이터 보정
- 예전 로직 때문에 `read_at`은 있으나 진도가 99.9% 미만인 항목은 클라이언트에서 읽음으로 취급하지 않음
- 해당 작품을 다시 읽고 진도를 저장하면 `clearLegacyRead`로 과거 잘못된 `read_at`을 D1에서 한 번 정리
- 실제 100%로 저장된 기존 읽음 데이터는 그대로 유지

### 서버 저장 규칙
- `/api/user/item` progress 저장은 더 이상 percent 값만으로 `read_at`을 생성하지 않음
- 클라이언트가 실제 마지막 지점 도달을 확인해 `read: true`를 보낸 경우에만 `read_at` 기록
- DB 컬럼 추가/마이그레이션 없음

## v7.5 — 이어보기 신뢰성 개선

- 긴 TXT에서 초반 스크롤이 1%가 될 때까지 저장되지 않던 문제 수정
- 진도율을 정수 1% 단위가 아니라 0.1% 단위로 저장하고, 24px 이상 실제 스크롤하면 최소 0.1%부터 기록
- 사용자에게 보이는 배지는 0.1~0.9%도 1%로 표시해 `읽는 중` 상태가 바로 보이도록 변경
- 첫 의미 있는 스크롤은 5분 대기 없이 즉시 D1에 저장
- 이후 읽는 동안에는 파일별 최대 60초 간격으로 원격 동기화해 저장 신뢰성을 높이면서 쓰기 부하는 제한
- `읽음` 기준과 이어보기 기준을 95%로 완전히 통일: 95% 이상 또는 `readAt`이 있으면 이어보기 대상에서 제외
- `읽는 중` 필터도 1% 이상이 아니라 진도율이 0보다 크면 바로 포함
- 일반 TXT와 대용량 chunk TXT 모두 동일한 0.1% 정밀도 규칙 적용
- 브라우저/탭 종료, 모바일에서 앱이 백그라운드로 갈 때 `pagehide`/`visibilitychange`에서 `fetch(..., keepalive:true)`로 마지막 위치를 한 번 더 저장
- 종료 저장은 동일 payload 중복 전송을 1.5초 동안 억제해 불필요한 D1 쓰기 방지
- 기존 `user_items.progress_percent REAL` 스키마를 그대로 사용하므로 DB 마이그레이션 불필요

## v7.0 — 안정화 기준본

### 1. 관리자 구조 분리
기존에는 `functions/admin.js` 하나의 거대한 문자열 안에 관리자 HTML/CSS/JS가 모두 들어 있었습니다.

v7부터 역할을 명확하게 분리합니다.

- `functions/admin.js`
  - 관리자 로그인 여부 확인
  - 로그인 HTML 또는 관리자 shell HTML 반환
  - **화면 CSS/동작 JS를 직접 포함하지 않음**
- `public/admin.css`
  - 관리자 화면 디자인의 단일 소스
- `public/admin-app.js`
  - 관리자 화면 동작의 단일 소스
- 관리자 API
  - 기존처럼 `functions/api/admin/*`에서 서버 동작 담당

`admin.css`와 `admin-app.js` 자체에는 비밀값이 없으며, 실제 데이터 조회/수정 권한은 기존 관리자 세션 + API에서 계속 검사합니다.

### 2. CSS 누적 덮어쓰기 금지
v6에서 가장 큰 UI 회귀 원인이었던

`기본 CSS → v6.xx override → 다음 버전 override → !important 재override`

방식을 중단합니다.

v7 규칙:

- 같은 컴포넌트의 새 버전 CSS 블록을 아래에 계속 추가하지 않음
- `theme.css`의 `V7 CANONICAL UI OVERRIDES` 안의 해당 섹션을 직접 수정
- `admin.css`의 `V7 ADMIN CANONICAL DESIGN` 안의 해당 섹션을 직접 수정
- `!important`는 레거시 `style.css`와 충돌하는 불가피한 경우 외에는 사용하지 않음
- Drive / POSTYPE 관리자 화면은 같은 색상·버튼·테이블 규칙 사용

### 3. 고정 반응형 구간
앞으로 breakpoint를 임의로 추가하지 않습니다.

- 모바일: `<= 640px`
- 태블릿: `641px ~ 1024px`
- PC: `>= 1025px`

태블릿은:
- 상단 필터 전용 한 줄 toolbar
- TXT 뷰어는 세로 독서형 최대폭 620px

### 4. TXT 뷰어 상태 규칙
뷰어 UI 상태는 세 개만 사용합니다.

- `normal`
- `reader-loading-locked`
- `reader-compact`

고정 규칙:
- 모바일 다운로드 / 북마크 / 닫기 버튼 44px
- compact 전환으로 닫기 버튼 크기·색상이 달라지지 않음
- loading 중에만 제목 header를 축소하고 progress를 위쪽에 표시
- 본문 로딩/chunk 렌더링 아키텍처는 변경하지 않음
- compact 진입/해제에는 넓은 hysteresis를 사용해 스크롤 깜빡임 방지

### 5. 필터 규칙
- 작품형태: 화면 표시는 `단편 / 연재`
- 내부 호환값은 `단편 / 연재물` 유지
- 상태: `연재중 / 완결`
- 필터 하나를 눌렀다고 다른 필터가 자동으로 바뀌지 않음
- 특히 작품형태/상태 선택이 출처를 자동 변경하지 않음

### 6. Drive 분류 규칙
- 200KB 이하: 자동 `단편`
- 200KB 초과: 자동 `연재`
- 수동 작품형태 override는 별도 KV에 저장
- 연재중/완결 상태 override도 별도 KV에 저장
- Drive 다시 읽기를 해도 수동 override 유지

### 7. POSTYPE 규칙
사용자/관리자 화면에는 복잡한 연결 구조를 노출하지 않습니다.

화면:
- 작품형태: `단편 / 연재`
- 상태: `연재중 / 완결`

내부:
- `post / series / manual`
- 기존 `publishType`, `linkType`, `manualUrls` 호환 유지
- `/series/`와 수동묶음 최근 발행일 로직 유지

### 8. 배포 규칙
- ZIP은 `public/`, `functions/`, `README.md`만 포함
- `wrangler.toml`, `.env`, `.dev.vars`, secret/config 파일 절대 포함하지 않음
- 관리자 ZIP uploader → GitHub commit → Cloudflare Pages 구조 유지
- 배포 후 GitHub commit / Cloudflare Pages 상태 표시 유지

### 9. V7 이후 패치 검증 체크리스트
패치를 만들기 전에 반드시 아래 검사를 통과시킵니다.

1. 변경 JS 전부 `node --check`
2. 관리자 shell의 DOM ID ↔ `admin-app.js` 참조 검사
3. 사용자 `index.html` DOM ID ↔ `app.js` 참조 검사
4. HTML 중복 ID 검사
5. CSS `{}` balance 검사
6. API 변경 시 request payload / 변수 선언 / Sheet column 위치 확인
7. 모바일 / 태블릿 / PC breakpoint가 기존 세 구간 밖에 새로 생기지 않았는지 확인
8. 기존 기능을 위한 backend API를 임의로 삭제하지 않음
9. README에 변경 이유와 영향 범위 기록

### 10. 이번 ZIP이 통합하는 핵심 파일
중간 배포 실패나 패치 누락의 영향을 줄이기 위해 v7.0만 예외적으로 현재 핵심 소스를 함께 포함합니다.

- 사용자: `index.html`, `style.css`, `theme.css`, `app.js`
- 관리자: `admin.js`, `admin.css`, `admin-app.js`
- Drive: `archive.js`, `drive-items.js`
- POSTYPE 등록/관리/동기화 API
- 배포 상태 API
- 누적 README

설정/Secret/Cloudflare binding 파일은 포함하지 않습니다.

## v6.78

### POSTYPE 시리즈 실제 API 사용
- 브라우저 Network에서 POSTYPE가 실제 시리즈 회차 목록을 불러오는 API 확인
- 형식: `https://api.postype.com/api/v1/series/{seriesId}/posts?sort=publishedAt,desc&sort=createdAt,desc&page=0`
- 기존 HTML/JSON 구조 추측 방식은 1순위에서 제거
- 이제 시리즈 최근 발행일은 POSTYPE 웹앱과 동일한 회차 목록 API를 직접 사용

### 최신화 판정
1. 입력된 `/series/{seriesId}` URL에서 `seriesId` 추출
2. POSTYPE 시리즈 posts API 호출
3. API가 이미 `publishedAt DESC`, `createdAt DESC`로 정렬하므로 현재 시리즈의 첫 번째 `POST` 항목 사용
4. 해당 `feedItem.publishedAt` Unix timestamp를 최근 발행일로 변환
5. 한국 서비스 날짜 경계에 맞춰 KST(+09:00) 기준 `YYYY-MM-DD`로 저장
6. 더 이상 1화/마지막 배열/HTML 링크 순서를 추측하지 않음

### fallback
- API가 일시적으로 실패하거나 회차가 비어 있을 때만 기존 시리즈 HTML 구조화 데이터 방식 사용
- 정상적인 경우 `strategy = series-api-first-post`

### 진단
- 응답에 `apiPostCount` 추가
- API에서 받은 현재 페이지의 회차 수 확인 가능
- 관리자 헤더를 `현재 버전 v6.78`로 갱신

- 로그인 상태에서는 스크롤 위치/긴 파일 chunk 위치를 사용자 계정에 저장
- 일반 파일은 `scrollTop + 진행률`, 810KB 이상 긴 파일은 `chunk 번호 + chunk 내부 위치 + 진행률` 저장
- 뷰어를 닫을 때 즉시 동기화하고, 장시간 읽는 경우 최대 약 5분 간격으로 중간 동기화
- 95% 이상 읽으면 `읽음` 상태 자동 기록
- 다른 기기에서 로그인해도 이어보기 가능

### 북마크 / 최근 조회
- 본문 상단에 `☆ 북마크` 버튼 추가
- 로그인 없이 북마크 버튼을 누르면 로그인 모달 자동 표시
- 최상단 `북마크`를 누르면 계정에 저장된 작품 목록 표시
- 작품을 열면 로그인 사용자에 한해 최근 조회 작품 자동 저장
- 최상단 `최근 조회`에서 최근 열어본 작품 최대 50개 확인 가능
- 북마크/최근 조회 목록에서 작품을 누르면 바로 본문 열기

### 도움말
- 새로고침 오른쪽에 `?` 도움말 버튼 추가
- `이어보기/북마크/최근 조회 작품을 저장하려면 로그인 후 감상해 주세요.` 안내 모달 제공
- 도움말 모달에서 바로 로그인 모달로 이동 가능

### 저장소
- 사용자 데이터 저장에는 Cloudflare D1 사용
- R2는 사용하지 않음
- D1 binding 이름: `USER_DB`
- 별도 SQL 실행 없이 최초 회원가입/로그인 시 필요한 테이블을 자동 생성
- 설정 파일은 패치 ZIP에 포함하지 않음

## v6.19

### 810KB 이상 긴 파일 렌더링 방식 변경
- 프로그래스바 종료 시간을 늦추는 방식만으로 해결되지 않던 긴 파일 멈춤 현상을 구조적으로 수정
- Google Drive + KV 본문 구조는 그대로 유지하고 R2/유료 저장소는 사용하지 않음
- 810KB 이상 파일은 전체 본문을 한 번에 DOM에 렌더링하지 않도록 변경
- 긴 본문을 브라우저 메모리에서 약 180,000자 단위로 나눔
- 처음에는 앞쪽 1~2개 조각만 화면에 렌더링하여 scrollbar를 빠르게 생성

- 추가 본문은 이미 다운로드된 텍스트를 브라우저 메모리에서 표시하므로 Google Drive/KV 추가 요청이 발생하지 않음
- 긴 파일 읽기 위치는 `chunk 번호 + chunk 내부 위치` 기준으로 저장하도록 보완
- 기존 퍼센트 기반 읽기 기록도 이어보기 시 긴 파일의 적절한 chunk 위치로 변환
